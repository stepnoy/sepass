#+TITLE: SE Pass: AutoFill с аппаратным ключом телефона
#+DATE: 2026-10-02

* Статус документа
Этот документ описывает прежний read-only прототип. Полный продукт
специфицирован в [[file:product/index.org][документации нового клиента]]; SEPass рассматривается как донор.

* Цель и границы первой версии
Пользователь выбирает SE Pass в системном AutoFill на iPhone/iPad, выбирает
запись, подтверждает Face ID/Touch ID и получает логин/пароль в Safari или
другом приложении. Секретный ключ P-256 остаётся в Secure Enclave. Совместимость
с обычными pass/prs и несколькими OpenPGP-получателями сохраняется.

Первый выпуск: только чтение уже синхронизированных записей. Без Git push,
редактирования, passkeys, TOTP AutoFill, NFC и отдельного Safari Web Extension.
Эти возможности не нужны для проверки основной гипотезы.

* Исходное состояние
Upstream SEPass: 21b08e3dd6c0bd94c76fb269bf49c0ca94841cad.
Приложение хранит clone и keyinfo.json в Application Support, обёрнутые
представления SE-ключей в приватном Keychain. Уточнение по исходникам:
HTTPS Git credential сериализуется вместе с GitRemote в UserDefaults;
его перенос в Keychain обязателен в новом продукте. SEPassCore содержит
OpenPGP-декодер, а KeyManager создаёт новый LAContext для расшифровки.
Биометрическая политика ключа: privateKeyUsage + biometryCurrentSet.
Менять криптографию или генерировать новый ключ для AutoFill не требуется.

* Архитектура
- Основное приложение: Git/import, управление ключом, явное включение AutoFill,
  публикация снимка после синхронизации и обновление системного индекса.
- Новый Credential Provider Extension: локальный поиск, выбор, Face ID,
  расшифровка одной записи и completeRequest с ASPasswordCredential.
- App Group: атомарно записанный снимок только шифротекстов, путей и публичного
  описания ключа. Complete file protection, исключение из backup.
- Отдельная shared Keychain access group: только обёрнутое dataRepresentation
  ключа расшифровки. Ни signing key, ни Git token, ни SSH key туда не попадают.
- Существующие приватные данные не перемещаются. Публикация для AutoFill
  включается явно; оригинальная связка остаётся источником истины.

Снимок имеет UUID поколения. recordIdentifier включает поколение и путь:
старое предложение после смены репозитория/ключа отклоняется. Снимок содержит
все нужные для чтения данные одной версии; файл заменяется атомарно.
Ключевые blobs адресуются по fingerprint. Включение нового снимка не должно
оставлять расширению ссылку на другой ключ. При отключении, удалении ключа
или очистке хранилища снимок и identity store очищаются.

* Поток AutoFill
1. Основное приложение публикует зашифрованные записи без их расшифровки.
2. Identity store получает только домен, метку записи и recordIdentifier.
   Логин в предложении является меткой пути, реальный login извлекается только
   после расшифровки. Массовая расшифровка ради индекса не выполняется.
3. Неинтерактивный callback отвечает userInteractionRequired. Никаких Face ID
   диалогов или выдачи паролей из неинтерактивного callback.
4. В интерактивном UI пользователь подтверждает конкретную запись. Создаётся
   новый LAContext, Secure Enclave разрешает ECDH после биометрии.
5. Из UTF-8 текста берутся первая строка (пароль) и первое непустое поле
   login:/username:/user: (регистр игнорируется). При отсутствии login
   используется имя записи. Значения не журналируются и не попадают в clipboard.
6. Выдаётся только выбранный ASPasswordCredential; ошибки/отмена не выдают пароль.

* Домен и недоверенные данные
Поиск по пути не требует расшифровки. Для автоматических предложений используется
только точное совпадение нормализованного домена из компонента пути.
Никакого includes/suffix matching: example.com.evil.test не является example.com.
Поддомены не наследуют пароль родителя автоматически. Ручной выбор другой записи
допускается только с явным подтверждением, если домен не совпадает.
Бинарные записи/пустые пароли отклоняются. Путь записи относительный, без ..,
скрытых компонентов и симлинков. Ограничиваются размеры записи, число записей
и суммарный размер снимка. Симлинки не следуются, в том числе у каталогов.

* Безопасность и восстановление
Face ID не является ключом шифрования: это условие использования SE-ключа.
AutoFill не экспортирует секретный P-256, но plaintext кратко существует в памяти
процесса и передаётся целевому приложению. Гарантированное обнуление всех Swift
String копий не заявляется. Симулятор использует программные ключи и НЕ доказывает
аппаратную безопасность. Изменение биометрии может инвалидировать ключ; доступ
восстанавливается другим OpenPGP-получателем (например YubiKey), затем новый ключ
телефона добавляется на Mac. Не менять существующую биометрическую политику.

* Подпись и доставка
App и extension должны иметь одну Apple Developer Team, общую зарегистрированную
App Group и Keychain group, capability AutoFill Credential Provider. Значения
вынесены в xcconfig; для форка используются собственные Bundle IDs.
App Store SEPass и локальный форк имеют разные контейнеры: установленный из Store
ключ не доступен форку. Для испытаний нужны отдельный ключ и тестовые записи.
В этой задаче PR не создаётся, публикация App Store/TestFlight не выполняется.

* Приёмка
- Unit: CRLF/UTF-8/пустой пароль, поля login, вредоносные домены и пути,
  симлинки, лимиты снимка, устаревшие record identifiers.
- Существующие OpenPGP roundtrip/interop tests продолжают проходить.
- Simulator + generic device сборки app и embedded extension.
- На физическом iPhone: включить provider в Settings, список/QuickType,
  Face ID success/cancel/failure, блокировка/перезагрузка, смена биометрии,
  старые предложения после удаления/смены store/key, запись на два получателя.
- Прямой тест AutoFill -> ECDH в Secure Enclave на устройстве обязателен прежде,
  чем утверждать готовность аппаратного сценария.
