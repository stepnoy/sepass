#+TITLE: Хранилище pass, получатели и безопасная запись

* Стандартная модель pass
pass вызывает GnuPG. Ближайшая .gpg-id в папке записи или среди её предков
задаёт набор получателей; вложенная политика заменяет родительскую, не объединяет.
Публичные ключи берутся из локальной связки GnuPG. Сам .gpg-id обычно содержит
отпечатки, а не ключевой материал. Добавление public key/отпечатка не меняет
получателей уже существующих файлов — нужна расшифровка и перешифрование.

Одна OpenPGP-запись: случайный симметричный session key шифрует содержимое;
отдельный PKESK для каждого получателя защищает этот session key его публичным
ключом. Любой один соответствующий секретный ключ открывает запись.
Резервные устройства с одинаковым ключом не являются дополнительными
независимыми получателями; отдельный ключ телефона является.

* Репозиторий нового клиента
#+begin_example
.gpg-id
.public-keys/<primary-fingerprint>.asc
my/example.com/main.gpg
work/example.org/account-<id>.gpg
work/.gpg-id                 # только если нужна другая политика
#+end_example

.public-keys — соглашение нашего клиента, не автоматическая функция pass.
На Mac публичные ключи нужно импортировать в GPG. Репозиторий хранит public
keys, ciphertext и политику, но никогда private keys, tokens, plaintext cache.
Публичные ключи могут раскрывать UID/email владельцев; предложить минимальный
UID при генерации и объяснить компромисс. В репозиторий не добавляется экспорт
секретного подключа даже с паролем.

Новый клиент P0 принимает только полные fingerprints в .gpg-id. Email, короткие
ID, локальные gpg group aliases и нестандартные selectors внешнего хранилища
не угадываются: сообщить о неподдерживаемой политике, оставить чтение доступным,
запись блокировать до явной нормализации. .gpg-id.sig при наличии нельзя
молча игнорировать: валидировать поддерживаемым доверенным signer либо
обозначить policy как неподдерживаемую и запретить запись.

* Разрешение и доверие ключам
1. Для пути найти ближайшую .gpg-id, отклонить пустой/повреждённый набор.
2. Разрешить полный primary fingerprint по .public-keys и локально импортированным
   публичным ключам; файл с неверным fingerprint не принимается по имени.
3. Проверить binding/self-signatures, назначение encryption, сроки и отзыв;
   выбрать подходящий encryption subkey, а не просто последний пакет.
4. Сравнить с локально подтверждённой политикой данного repositoryID/папки.
5. Только после этого разрешить запись. Нехватка хотя бы одного public key —
   отказ с объяснением, а не шифрование только на доступные ключи.

Важно: совпадение fingerprint с .gpg-id обнаруживает несоответствие файла,
но не защищает от изменения злоумышленником ОБОИХ файлов. Первый набор
подтверждается по доверенному каналу, изменения состава — явным действием
после показа diff. Локальная база утверждённых fingerprints не перезаписывается
данными из Git. В дальнейшем можно добавить подписанную policy доверенным
администратором; это отдельный протокол с правилами ротации, не магическое
доверие к любому подписанному commit.

* Совместимость криптографии первого выпуска
Обязательный writer: несколько PKESK в одном сообщении, RSA-3072/4096 для
существующего аппаратного получателя и P-256 ECDH для Secure Enclave телефона,
AES с проверкой целостности и совместимостью с проверенными GPG/prs версиями.
Согласование алгоритмов учитывает предпочтения всех получателей; несовместимость
выдаёт ошибку, а не понижает защиту или исключает получателя.

Reader: бинарный/armored OpenPGP, свой P-256 подключ среди других получателей;
явные границы версий пакетов, compression, KDF, AES и integrity protection.
Legacy ciphertext без защиты целостности не принимается. Новые AEAD/v6/curve
варианты не объявляются поддержанными без fixtures и аппаратных проверок.
Матрицу конкретных версий библиотек фиксировать при crypto spike.

* Текст записи: совместимость без обязательной новой схемы
Первая строка — пароль в точных байтах UTF-8; пробелы не обрезаются.
Далее распознаём login:/username:/user:, email:, url:/website:, title: и
otpauth:// URI. Для логина приоритет задаётся единообразно всему приложению:
первое непустое login/username/user, затем email, затем явный ручной выбор;
имя файла допустимо лишь как fallback с предупреждением, не как основной источник.

Повторяемые URL сохраняются. Парсер хранит исходные строки/CRLF, неизвестные
поля, дубликаты и порядок; редактор меняет только выбранные значения.
При неоднозначности показать raw-text режим, не уничтожать поля нормализацией.
Бинарные данные: чтение/экспорт как opaque ciphertext; текстовый редактор и
AutoFill не должны превращать их в строку с replacement characters.

Новые заметки: пустая первая строка + type: note + title/тело. Другие текстовые
типы можно сохранить, но специализированные функции не обещаются. Многострочный
пароль не сериализуется в обычный pass-login незаметно: ошибка и raw-note вариант.
Не вводим обязательную БД в репозитории: pass/prs должны работать без приложения.

* Метаданные и имена
Хранить title, login, email, заметки, теги внутри .gpg. Поиск не зависит от
имени файла. Полностью скрыть дерево каталогов и историю изменений обычный
pass не позволяет. Домены/папки тоже метаданные; opaque naming — опция.
Внутренний ID записи (например x-client-id) необязателен и не является
единственным источником идентичности после внешних копирований.

* Транзакции
Создание/редактирование:
- Проверить expectedCiphertextOID, policy hash, допустимость пути и всех ключей.
- Сформировать текст в памяти; encrypt для полного набора получателей.
- Проверить структуру PKESK, целостность формата и roundtrip собственным ключом,
  если текущий клиент является получателем. Запись в папку без собственного
  получателя требует явного режима и предупреждения о потере чтения.
- Шифротекст и operation journal записать атомарно/долговечно; связать
  (operationID, baseCommit, beforeOID, afterOID, policyHash, path).
- Лишь после устойчивого commit локальной транзакции показать «Сохранено».

Журнал содержит шифротексты/ссылки/OID, а не plaintext. Сбой после сохранения,
но до создания Git commit, восстанавливается идемпотентно по operationID.
Отмена не удаляет уже подтверждённое пользователю сохранение.

Перемещение: одинаковая политика — можно перенести ciphertext. Другая политика —
расшифровать и перешифровать для получателей назначения до удаления источника.
Внешний File Manager rename может оставить старых получателей: проверка
соответствия сообщает об этом, но не считает вывод по короткому key ID строгим
криптографическим доказательством. Для сообщения с hidden recipients нельзя
полностью восстановить состав по PKESK; требуется повторное encrypt по policy.

Удаление: пользователь подтверждает; локальная операция сохраняет ссылку на
предыдущий ciphertext для undo. Git-история не очищается обещанием «Удалено».
Удаление последней записи папки не должно случайно потерять её .gpg-id.
Симлинки не следуются, submodules/hooks/filters не выполняются; относительные
пути проверяются на traversal, Unicode/case collisions и выход из контейнера.

* Изменение получателей
Добавить public key → проверить/утвердить fingerprint → построить план всех
затронутых записей с учётом вложенных .gpg-id → decrypt/encrypt в staging →
проверить весь набор → одной согласованной публикацией применить policy+files.
Если часть файлов недоступна, показать точный незавершённый план; не объявлять
миграцию законченной. Прогресс возобновляется только при неизменных base OID
и policy. Состав получателей — конфликт безопасности, не обычный текстовый merge.

Удаление получателя закрывает новые версии, но не старые ciphertext в Git,
backups и клонах. При компрометации нужны смена самих паролей и отзыв сервисных
сессий; Git history rewrite не отзывает уже скачанные данные.
