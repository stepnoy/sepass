#+TITLE: Автоматическая синхронизация и конфликты

* Что значит «автоматически обновляется»
Это прежде всего обновление содержимого Git. Доставка новой версии самого app
происходит через App Store/TestFlight и системные настройки обновлений;
приложение не устанавливает произвольный новый исполняемый код из Git.

Foreground: fetch при запуске/возврате (если последняя проверка старше 60 s),
после восстановления сети, по ручному Refresh; периодическая проверка каждые
5 минут только пока app активно. После изменения debounce отправки 2 s,
серия изменений объединяется без потери локальной долговечности.
Тайминги — начальные продуктовые настройки, не обещание точного SLA сети.

Background: BGAppRefresh/BGProcessing как best effort. iOS выбирает время,
учитывает питание/настройки, может не запускать задачу после force quit.
Нельзя обещать «каждые 5 минут при закрытом приложении». Всегда есть foreground
catch-up и видимый timestamp. APNs/webhook relay не нужен для P0; при появлении
требует отдельного backend и модели утечки метаданных.

* Авторизация в фоне
Никаких Face ID запросов в background. Фоновая работа может получать и
проверять ciphertext, отправлять уже готовые согласованные commits.
Операции, требующие decrypt/изменения получателей, ждут foreground+unlock.

Git credentials — приватный Keychain. Default WhenUnlockedThisDeviceOnly:
задача на заблокированном устройстве может отложиться. Дополнительный режим
фонового доступа может хранить ТОЛЬКО сетевой credential как
AfterFirstUnlockThisDeviceOnly после явного согласия; это не ослабляет ACL
ключа расшифровки. До первого unlock после reboot фон не обещается.
App Group с complete file protection может быть недоступен при lock;
публикацию откладывать. Не понижать защиту snapshot ради расписания.

* Машина состояний
idle → scheduled → fetching → validating → integrating → committing → pushing
→ publishing → idle.
Отдельные терминальные/ожидающие состояния: offline, authRequired, locked,
conflict, recipientApprovalRequired, rateLimited, cancelled, storageFull.

На один repositoryID только один writer/sync actor. Параллельные события
coalesce, не запускают конкурирующие clone. Сохранять base/local/remote OID,
operationID, retry state и журнал на диск. Повтор после crash идемпотентен.

* Pipeline
1. Убедиться в долговечности локальных операций и корректности рабочего дерева.
2. Fetch refs/objects в изолированное хранилище, ограничить размеры и время.
3. Проверить пути, дерево, `.gpg-id`, public keys, rollback/переписанную историю.
4. Если новых local operations нет — fast-forward проверенного дерева.
5. Если обе стороны менялись — определить merge-base и построить three-way план.
6. Независимые изменения объединить; спорные оставить в encrypted conflict store.
7. Повторно проверить политику каждого локального изменения. Новая remote policy
   требует подтверждения и, если нужно, перешифрования локальных записей.
8. Создать локальный commit/merge commit, push без force. Non-fast-forward →
   новый fetch и повтор merge, bounded retry; не сбрасывать локальный commit.
9. При успехе обновить lastSyncedHead. Snapshot для чтения/AutoFill может содержать
   проверенные локальные pending изменения, но статус не должен называть их synced.

Публикация согласованного локального snapshot не обязана ждать сети. Ни
недоверенная policy, ни нерешённая конфликтная версия не становятся активным
секретом AutoFill. Для конфликтной записи оставляем последнюю однозначную
версию с меткой конфликта либо блокируем fill; выбор закрепить UX-тестом.

* Таблица конфликтов
| Base/local/remote | Поведение |
| Изменены разные файлы | Автоматический merge ciphertext |
| Один файл изменён только одной стороной | Применить изменённую версию |
| Обе стороны получили одинаковый blob | Не конфликт |
| Один файл изменён обеими сторонами | Не merge ciphertext; показать обе версии после unlock |
| Удаление против изменения | Сохранить изменённый ciphertext, запросить решение |
| Rename против изменения | Сопоставить по ancestry/blob/ID с проверкой неоднозначности |
| Два новых одинаковых пути | Сохранить оба, явное имя второго/решение |
| Меняется .gpg-id или public keys | Барьер политики; без автоматического объединения получателей |
| Переписан remote history/нет merge-base | Остановить автоматический sync; сохранить локальную историю |

Для одного конфликта доступны «моя», «удалённая», «сохранить обе» и ручное
объединение полей. Последнее требует decrypt доступных версий. При недоступном
ключе обе ciphertext версии сохраняются, но содержимое не выдумывается.
Не создавать conflict markers внутри .gpg. Field-level merge пароля никогда
не выбирает «новее по timestamp» автоматически. Удаление на одном устройстве
не должно воскресать молча после offline sync другого.

* Сбой, отмена и retry
Network timeout → экспоненциальная задержка с jitter (начало 2 s, потолок 5 min),
немедленная попытка по явному действию/восстановлению связи, без busy loop.
401/403 → нет автоматического бесконечного retry; показать credential/permission
ошибку. TLS/SSH host key mismatch → остановка, не предлагать insecure bypass.
Сбой диска/kill между стадиями → восстановить staging/journal, не удалить
последнюю проверенную версию. Ограничения Git pack/decompression — обязательны.

Commit messages — нейтральные действия/operationID, не login/password/notes.
Git author может раскрывать email: настройка pseudonymous author и объяснение.
Нельзя выполнять remote hooks, filters, LFS helpers или shell из репозитория.

* Внешние клиенты
pass/prs могут менять файлы без operation journal. Их изменения обнаруживаются
по Git blobs/paths. Отсутствие внутреннего UUID нормально. Обход файловой
системы не следует symlink и не запускает external diff/textconv.
Если пользователь переместил ciphertext в папку с другой политикой на Mac,
клиент показывает рассогласование и план исправления, не обещает, что move
самостоятельно изменил получателей.
