#+TITLE: Поиск по содержимому, сессия и AutoFill

* Два вида поиска
Стандартный pass find ищет имена; pass grep расшифровывает и ищет содержимое.
Новый клиент реализует оба поведения. Сначала мгновенно фильтруются пути;
после авторизации добавляются совпадения из login/email/title/URL/notes.
Поиск по паролю, TOTP secret и произвольному raw-тексту — явный расширенный режим.
Пароль никогда не показывается в snippet, даже если совпал запрос.

* Базовая реализация без обязательного постоянного индекса
1. Захватить immutable snapshot и поколение запроса; debounce ввода 200–300 ms.
2. Получить UnlockSession пользователя. Обходить записи с ограниченной
   параллельностью, сохраняя отменяемость и очередь аппаратных операций.
3. Decrypt одной записи → parse → сравнить нормализованные поисковые значения →
   сохранить только нужный результат/поля в memory-only кеше сессии.
4. Публиковать результат постепенно с count scanned/total и count unavailable.
5. Новая строка запроса отменяет старые результаты через generation token;
   plaintext-кеш уже обработанных записей можно использовать внутри той же сессии.
6. Изменение ciphertext invalidates соответствующую запись; блокировка
   invalidates весь plaintext/search cache и authentication context.

Не расшифровывать всю базу при каждом символе. Положительный кеш минимальных
поисковых полей разрешён на время разблокированной сессии; полные пароли
не удерживать ради обычного поиска. Для поиска «всё содержимое» отдельный
отменяемый проход. Ошибка одной записи не превращает остальные в «не найдено».
Недоступные получатели не вызывают десятки одинаковых запросов Face ID.

Нормализация: Unicode casefold для поиска, сравнение email без изменения
хранимого значения, поиск кириллицы/латиницы как текстовых данных. Транслит
имён файлов не означает транслитерацию паролей. Подсветка только разрешённых
полей; запросы и matched snippets не сохраняются в логи/аналитику/Spotlight.

* Биометрическая сессия — обязательный эксперимент
Текущий донор создаёт LAContext на каждую расшифровку. Требование продукта:
одна осознанная разблокировка для пользовательского сеанса поиска, а не
сотни повторных окон. Проверить повторное использование одного LAContext с
ключом biometryCurrentSet на реальном Face ID и Touch ID устройстве.
Не делать вывод о Face ID из свойства с названием Touch ID reuse duration.

Предложенные defaults: блокировка при уходе в фон и при выключении экрана,
2 минуты бездействия в foreground; при временном системном запросе биометрии
не спутать inactive с уходом пользователя из app. Значения уточнить UX-тестом.
Отмена завершает операцию, invalidate context и прекращает выдачу результатов.
Секретный P-256 не извлекается из SE; plaintext и session keys кратко бывают в RAM.

Если единый context не обеспечивает приемлемое число запросов/скорость,
это release blocker SEARCH-01. Разрешённые следующие исследования: отдельный
локально зашифрованный индекс с отдельным аппаратно защищённым cache key и
чётким отзывом; пересмотр unlock policy только явным решением. Нельзя незаметно
ослаблять ACL исходного ключа или сохранять расшифрованную БД на диск.

* AutoFill: общий смысл, отдельный процесс
Использовать ASCredentialProviderViewController с современными callbacks.
Noninteractive callback при отсутствии допустимой сессии возвращает
userInteractionRequired; не вызывает Face ID за кадром.
Interactive: актуальный snapshot → выбор → локальная авторизация расширения →
проверка поколения/политики → decrypt → username/password → completeRequest.
Сессия основного приложения не считается автоматически сессией расширения.
Отмена, блокировка, отзыв ключа или смена snapshot до выдачи прерывают запрос.

Без индексирования системных подсказок P0 всё равно должен работать:
пользователь открывает SEPass/новый provider из AutoFill и ищет по login/URL
внутри расширения после разблокировки. Непрозрачный filename не мешает поиску.
Бюджет расширения ограничен: paging/ограниченный кеш, измерение памяти,
честное сообщение при слишком большом store; не усекать список молча.

* Метаданные и QuickType
Системный ASCredentialIdentityStore может содержать домен, user-label и opaque
recordIdentifier. Это сознательная публикация метаданных iOS за пределами
нашего шифротекста; пароль и TOTP secret туда не попадают.

Default: не публиковать реальный login; label — безопасное имя/alias.
Домен из пути можно индексировать без decrypt. Для непрозрачных путей URL
можно извлечь после unlock и публиковать только при отдельном opt-in.
Без такого opt-in доступен поиск в provider, а быстрые site suggestions могут
отсутствовать. Нельзя одновременно обещать скрыть все домены от системы и
иметь полный незашифрованный системный индекс сопоставления.

При sync обновлять только проверенное поколение. Устаревший recordIdentifier
никогда не выбирает новый секрет по старому пути. Disable/удаление store/key
отзывает snapshot, shared key reference, identity store. Ошибка очистки видна.

* Сопоставление сайтов
Default — точный нормализованный hostname из URL, включая корректный IDNA.
Не использовать substring/suffix matches. example.com.evil.test не example.com.
Связывание поддоменов и Android/iOS associated domains — отдельные проверенные
правила; не выводить доверие из похожего display name приложения.
Ручной выбор несовпадающего сайта требует подтверждения с видимым получателем.
Протокол/host/port хранить раздельно; URL userinfo и необычные схемы не подменяют host.

* Проверяемые показатели
Целевые, пока НЕ измеренные: отклик на ввод <100 ms; отмена <300 ms;
первые совпадения <2 s после авторизации на 1000 типичных записей;
полный холодный поиск на 1000 записях <10 s. Тестировать 100/1000/10000 записей,
старейший поддерживаемый iPhone, offline/locked/cancel/foreground return.
Если полный поиск не укладывается, не объявлять критерий выполненным:
изменить архитектуру кеша через ADR и повторить security review.
